# ADR-0003：AnalysisJob 使用统一状态迁移入口

## Status

Accepted

## Date

2026-10-27

## Context

HTTP、消息重投、并发消费者、取消和恢复都会尝试推进任务。让各调用方直接写状态会产生乱序迁移、重复计费和不可恢复的任务。

## Decision

所有 `AnalysisJob` 状态只能经由 `JobTransitionService` 改变。迁移必须校验允许的前置状态和版本，并与阶段记录、Outbox 事件在同一事务中提交；数据库 CAS 是并发裁决，不能由 Redis 锁替代。

主状态从创建、排队、消费、解析、建上下文、索引、回答、验证走向完成；重试、取消、失败、死信和人工 Replay 是受控分支。终态不得被普通消息再次推进，Replay 也不能通过重投旧消息伪造。

错误使用稳定分类而非异常类名，至少区分可重试、不可重试、未知结果、取消和预算耗尽。未知结果不能被当作“肯定没执行”。

## Alternatives Considered

- 各 Controller/Consumer 直接更新：无法统一 CAS、事件和非法迁移规则。
- 依赖 RabbitMQ 顺序：重投和并发下不成立。
- 所有错误自动重试：会掩盖输入错误并放大成本。

## Consequences

- 新增状态或修改迁移边会影响 API、消费者、恢复和运维，必须新增 ADR。
- 状态机是业务真源；消息、缓存和锁都不能绕过它。
- M1/M4 必须用状态机测试和故障测试证明这些约束，但实现细节不在本 ADR 固化。

## Validation

- 未声明的迁移被拒绝，并发旧版本只有一个迁移成功。
- 重复消息在已完成阶段成为安全 no-op。
- 不可重试、未知和预算耗尽错误不会进入无界重试。
