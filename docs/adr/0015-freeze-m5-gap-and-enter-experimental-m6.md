# ADR-0015：冻结 M5 效果缺口并受限进入实验性 M6

## Status

Accepted

## Date

2026-11-10

## Context

候选 `5e71014` 的 M5 正式 DEV 三轮证明评测工程链路可运行，但严格 Claim-Evidence
支持率仅为 `28.57% / 46.67% / 54.55%`，引用定位率仅为
`82.35% / 77.78% / 84.62%`，均未达到 `85% / 95%` 硬门。分阶段入口因此没有重跑
TEST。继续只优化单次回答可能推迟验证 M6 的核心假设：受预算约束的补检和扩窗是否能改善复杂题。

项目负责人明确要求先冻结 M5 问题并优先进入 M6。该决定改变里程碑依赖顺序，但不授权
降低质量门、改写历史、使用 TEST 调参或把实验能力默认发布。

## Decision

- M5 保持“未退出”；保留最新失败指标、报告和历史 TEST，不修改题目或阈值。
- 以 `EX-2026-11-10-M6` 受限进入 M6。例外只覆盖里程碑顺序，2027-02-08 到期。
- M6 Agent 默认关闭，仅作为本地实验路径；非 Agent 基线继续是默认产品行为。
- 第一版只实现一个模块内的有界循环和一个窄 Tool Registry，不引入插件框架、通用工作流、
  多 Agent、动态类加载或模型直连数据库/网络/文件。
- `AgentRun`、`AgentStep`、`ToolCall` 和 Observation 摘要以 MySQL 为真源。Redis 只能投影；
  清空后必须可从 MySQL 回放。
- Java 在每一步前确定性执行 owner、schema、幂等、工具白名单、step/deadline/token/费用/
  修复次数硬门。模型输出无权修改预算、权限、引用或终止状态。
- 每个 Run 必须记录稳定 `policyVersion`、完整预算快照和明确 `terminationReason`。恢复只从已提交
  Step 之后的安全边界继续；未知工具结果不得自动重复高成本调用。
- M6 的 DEV/challenge A/B 可以用于开发；历史 TEST 保持封存。只有第 8.3 节晋级条件和 M5
  原硬门同时满足，Agent 才能默认启用或形成效果宣称。

## Minimal Loop

MVP 只保留三种动作：检索证据、扩展现有证据时间窗、基于选定证据生成并验证答案。工具结果
不足时确定性拒答；最多 6 个 Tool Step、最多 2 次答案生成/修复，并受现有调用、计量、费用和
deadline 硬门约束。澄清先以明确终止原因和用户提示表达，不建设多轮会话状态机。

## Alternatives Considered

- 继续阻塞 M6 直到 M5 通过：流程最严格，但无法验证动态补检是否正是当前质量缺口的有效路径。
- 把 M5 标记通过：与实际指标冲突，拒绝。
- 提高预算或放宽证据门：会掩盖问题并增加费用，拒绝。
- 先建设通用 Agent/插件框架：MVP 没有第二个实现需要该抽象，拒绝。

## Consequences

- 可以在保留失败基线的前提下验证最小动态路径，减少继续优化错误层级的风险。
- M6 即使工程完成也可能因 M5 原门或 Agent 晋级门失败而保持实验状态。
- 例外到期前必须由负责人选择：修复并完成双门、续期并说明新证据，或关闭实验路径。

## Validation

- 文档和 UI 始终区分“M5 未退出”“M6 实验中”“Agent 已晋级”。
- 自动化证明 Redis 清空可回放、重启可恢复、越权工具和超预算调用在执行前被拒绝。
- 至少三类工具结果产生不同路径，且每条路径有稳定终止原因。
- DEV/challenge 与冻结非 Agent 基线同题 A/B；TEST 在候选冻结和 DEV 双门通过前不运行。
